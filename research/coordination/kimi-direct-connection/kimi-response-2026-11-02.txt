## 1. Мой интерфейс и инструменты генерации (проверено сейчас)

**Интерфейс:** веб-версия Kimi (агентный чат) с изолированной Linux-песочницей для выполнения кода. Это не Kimi Code CLI — другой продукт с другим набором инструментов.

**Генерация изображений** — плагин `image_generation`. Проверено: он вызывает метод `generate_image` шлюза **agent-gw** (внутренний backend-шлюз Moonshot, «Kimi For Coding Backend») через проприетарный Python SDK `agent-gw` (установлен, версия 0.3.0). Параметры: текстовое описание, размер (до 3840 px, соотношение до 3:1), прозрачный фон (PNG), референсы — только по публичным URL. Лимит — 20 одновременных генераций, таймаут запроса 450 с.

**Генерация 3D** — плагин `model3d_generation`, работает через тот же шлюз agent-gw, движок — **Tripo API**. Режимы: text→GLB, image→GLB, multiview→GLB; модели v3.1/v3.0/v2.5 и low-poly p1/p2; постобработка: retexture, сегментация, decimate (LOD), complete. Входные модели — GLB/GLTF/FBX/OBJ/STL до 150 МБ, таймаут задачи 900 с.

Ключевой факт: оба плагина — это тонкие Python-обёртки над SDK `agent-gw`. Я проверил состав SDK: клиент имеет методы `upload_storage`, `download_storage`, `chat_completion`, `search`, `fetch`, а `ToolsAPI` — `generate_image`, `generate_3d_model`, `generate_video`, `generate_speech` и др. Аутентификация: `KIMI_API_KEY` или `~/.kimi/agent-gw.json`.

## 2. Есть ли у этого интерфейса API

**Проверено по документации:** публичного API именно для веб-чата (отправить задание в конкретный диалог, продолжить его, забрать файлы) нет. Официальная справка прямо разделяет: «Kimi на вебе — разговорный продукт для пользователей; Kimi API — сервис для разработчиков», с раздельным биллингом.

Что существует вместо этого:

- **Kimi API** (platform.kimi.ai): chat completions, есть Files API — загрузка файлов и вопросы по ним, включая изображения. Это stateless-диалог, а не «моя» сессия с плагинами.
- **Kimi Code CLI**: headless-режим `kimi -p "..."`, сессии с resume, MCP-клиент. API-эндпоинт совместим с OpenAI и Anthropic протоколами: `https://api.kimi.com/coding/v1` (Китай) / `https://api.kimi.ai/coding/v1` (overseas).

Итог: «продолжить именно этот диалог программно» — нельзя. Codex может вызывать либо Kimi CLI, либо те же backend-инструменты напрямую (см. п. 3).

## 3. Подключение моих инструментов генерации к установленной Kimi CLI

**Проверено:** генерация у меня идёт через SDK `agent-gw`, а не через внутренности веб-чата. Значит, CLI не нужно «подключаться ко мне» — ему нужен доступ к тому же шлюзу. Два рабочих варианта:

**Вариант A (проще, рекомендую): Codex/скрипт вызывает agent-gw напрямую, без CLI.**
Требуется на Mac:
1. `pip install agent-gw` (пакет проприетарный; проверьте доступность в вашем канале распространения — у меня он предустановлен, публичность на PyPI я не проверял).
2. Ключ: `KIMI_API_KEY` или `~/.kimi/agent-gw.json`.
3. Вызовы: `client.tools.generate_image(...)`, `client.tools.generate_3d_model(...)`, `client.upload_storage(...)` для референсов, `download_storage` для результатов.

**Вариант B: обернуть agent-gw в локальный MCP-сервер и подключить к Kimi Code CLI.**
CLI официально поддерживает MCP по stdio и HTTP, конфигурация в `~/.kimi-code/mcp.json` (user-level) или `.kimi-code/mcp.json` (project-level). Пример добавления stdio-сервера: `kimi mcp add --transport stdio gen -- python3 /path/to/gen_mcp_server.py`. Важный нюанс для headless-запусков `kimi -p`: project-level MCP-серверы в недоверенной папке отключены — нужно `KIMI_CODE_TRUST_WORKSPACE=1`. Тогда Codex вызывает `kimi -p "сгенерируй ... через MCP-инструмент generate_3d"`, и CLI сам дёргает шлюз.

Вариант A надёжнее для автоматизации: меньше звеньев, статус и файлы контролирует ваш код, а не парсинг вывода агента.

## 4. Как Codex будет обмениваться файлами и статусом

Проверенная механика шлюза хорошо ложится на автоматизацию:

- **Референсы (картинки):** локальный файл → `upload_storage` → публичный `signed_url` → передаётся как `reference_image_urls` в генерацию. Шлюз принимает только публичные URL, локальные пути отклоняются.
- **GLB на вход:** тоже нужен публичный URL (`--model-url`, до 150 МБ) — тот же `upload_storage`.
- **Результаты:** генерация возвращает `media.url` + `mime_type` (изображения) и `task_id` + URL GLB (3D). Скачивание — обычный `curl`/HTTP.
- **Статус:** для 3D есть `task_id` — по нему же делаются правки: `texture`, `segment`, `decimate`, `complete` принимают `--task-id` предыдущей задачи. Это и есть канал «замечаний на доработку»: Codex кладёт вердикт, скрипт запускает retexture/decimate по сохранённому `task_id`, не перегенерируя с нуля. Логи задач (Job log + PID file) — готовый механизм слежения; лимиты ожидания 450 с (изображения) / 900 с (3D).

## 5. Минимальный рабочий протокол (общая папка заданий)

Поскольку прямого канала «Codex → этот диалог» нет, наиболее близкий поддерживаемый вариант — **папка-очередь + локальный worker на agent-gw**. Codex остаётся оркестратором, Kimi CLI не обязателен.

Структура в `/Users/dmitrij/cockpit/kimi-jobs/`:

```
inbox/<job_id>.json      # задание от Codex
refs/<job_id>/           # референсы, GLB
status/<job_id>.json     # queued|running|done|failed, task_id, urls
out/<job_id>/            # результат (png/glb) + превью
log/<job_id>.log         # лог worker'а
```

Формат задания:
```json
{
  "job_id": "cockpit-seat-007",
  "op": "generate_3d",
  "model": "v3.1",
  "description": "...",
  "face_limit": 10000,
  "refs": ["refs/cockpit-seat-007/front.png"],
  "revision_of": "cockpit-seat-006",
  "fix": "сделать спинку тоньше, сохранить геометрию подушек"
}
```

Цикл:
1. **Отправка:** Codex пишет `inbox/<job_id>.json` + референсы.
2. **Подтверждение:** worker атомарно переносит файл в `status/` с `state: running`, загружает референсы через `upload_storage`, сабмитит задачу, пишет `task_id` в статус.
3. **Выполнение:** polling по `task_id`; для правки — если `revision_of` задан, вызывается `texture`/`decimate`/`complete` по старому `task_id`, а не новая генерация.
4. **Получение:** файл скачивается в `out/`, статус → `done`, Codex забирает GLB и preview.png.
5. **Проверка:** Codex сам верифицирует (face count, размеры, визуальный осмотр превью).
6. **Исправления:** новый job с `revision_of` → шаг 2. Храните `task_id` всех версий — это дешёвые правки вместо полных перегенераций.

**Авторизация:** один ключ Moonshot в `~/.kimi/agent-gw.json` на стороне worker'а. **Ограничения:** 20 параллельных генераций (429 при превышении), таймауты 450/900 с, входные модели ≤150 МБ, референсы только по URL. **Стоимость:** биллинг идёт через Kimi For Coding / API-аккаунт и отдельно от веб-подписки — точные тарифы на генерацию изображений/3D я проверить не смог, смотрите platform.kimi.ai перед запуском.

## Что подтверждено, а что предположение

**Проверено сейчас:** состав SDK agent-gw 0.3.0 и его методы, механика плагинов (upload → URL → generate → download, `task_id` для правок, лимиты и таймауты из их документации).
**Подтверждено официальными источниками:** у веб-чата нет API; MCP-поддержка и конфигурация в Kimi Code CLI; headless-ограничение с trust; совместимые API-эндпоинты; Files API в Kimi API.
**Предположения (требуют проверки на вашем Mac):** что пакет `agent-gw` доступен для установки вне моей песочницы; что ваш ключ имеет доступ к `generate_image`/`generate_3d_model`; точная стоимость вызовов; поведение `upload_storage` вне моей среды. Рекомендую начать с одного тестового вызова `generate_image` из простого Python-скрипта — если он проходит, весь протокол из п. 5 работоспособен.
