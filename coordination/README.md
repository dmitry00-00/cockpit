## Цикл координации

1. Проверить рабочую копию, общий baseline и исходники. Зафиксировать задачу/ветку/владельца.
2. Доставить содержимое конкретного task-файла. Сохранить реальный session/process/job id.
3. Kimi подтверждает scope, запускает нужных агентов, сообщает блокеры и проверяемый результат.
4. Codex читает diff и результаты, запускает интеграционные проверки, возвращает конкретные замечания.
5. После исправлений Codex принимает результат и обновляет общий backlog. `submitted` не равно `accepted`.

Статусы: prepared → delivered → running → submitted → changes_requested/accepted.
`blocked` содержит точную причину и требуемое действие. Статус процесса проверяется по живому
handle/API/подтверждению runner, а не по старому lock-файлу. Не перезапускать задачу только из-за
таймаута наблюдения. Дублирующий запуск может изменить те же файлы одновременно.

## Работа без присутствия владельца

В рамках работающей сессии Codex самостоятельно дробит задачи, проверяет результаты и возвращает
правки Kimi. Рутинные обратимые действия в согласованном scope не требуют постоянных вопросов.
Недостающий факт не заменять выдумкой: продолжать независимую работу и записывать блокер.

Для работы после остановки сессии необходим отдельный runner/поддерживаемая автоматизация:
живой процесс, доступ к репозиторию/инструментам, очередь, журнал, ограничение ресурсов и механизм
доставки результатов обратно координатору. Сейчас такой runner не настроен и не запущен.
Простое наличие ключа GitHub этого не обеспечивает. Владелец может остановить всю очередь;
нельзя самостоятельно обходить эту остановку расписанием или фоновым процессом.
