## Принцип

Единым делаем форму, а не содержание. Мета-шаблон — это фиксированный набор слотов с неизменным порядком и id. Конкретный вид субъекта (персонаж, группа, организация/город, государство) задаёт SlotSpec: схему, подписи, иконку и рендерер. Пустой слот скрывается, но не исчезает из шаблона.

У каждого слота три слоя, как в вашем правиле «справочник ≠ состояние»:

flowchart TB
  S[Subject — мета-шаблон]
  S --> R["Справочный слой (RO)<br/>refId → content/*, источник"]
  S --> T["Слой состояния (event-sourced)<br/>меняется только событиями и патчами"]
  S --> D["Производный слой (проекция)<br/>derive() из состава и контекста"]
  R -.-> T
  T --> DПроизводный слой даёт то, что связывает масштабы. Группа считается из персонажей, организация из групп и мест, государство из организаций и территорий. Контекст при этом идёт вниз:

flowchart LR
  C[Персонаж] -->|rollup| G[Группа] -->|rollup| O[Организация / город] -->|rollup| S[Государство]
  S -.->|контекст: условия, модификаторы| O -.-> G -.-> C## Слоты: общее и различия

Слоты 1, 7, 8, 10 не зависят от масштаба. Слоты 2–6 меняют только содержимое: рендерер один. Слот 9 единственный, где различается сама геометрия.

## Экраны

| Экран | Единая рамка | Что меняется по масштабу |
|---|---|---|
| Карта | лестница уровней, слои, выбор, LOD | тип геометрии; модель движения. События перемещения нет: нужно SUBJECT_MOVED{from, to, geom} |
| Время | одни мировые часы, untilSec, очередь событий | темп: раунд → час/день → десятидневка → сезон/год; у субъекта поле cadence |
| Состояние | EntityCard: корешок = ядро, полоса показателей = жизнестойкость + топ-осей, вкладки = остальные слоты | набор вкладок и подписи из SlotSpec |
| Бой / небой | Interaction{sides, order, actions, resolve, outcome→WorldDelta} | режим: инициатива и раунды против переговоров, торговли, интриги, осады |

Бой и небоевое взаимодействие — два режима одного Interaction. Ваш Encounter становится его частным случаем с mode: 'combat'.

Правило между масштабами: взаимодействие идёт только между субъектами одного уровня. Разные уровни связаны только через rollup вверх и контекст вниз. Война государств — это состояние на городах и группах плюс отдельные бои, открытые на уровне группы и персонажа.

## Мета-шаблон (статичный контракт)

interface Subject<K extends Kind = Kind> {
  id: string; kind: K; scale: 1|2|3|4
  refId?: string; parentId?: string
  slots: {
    vitals:    Vital[]
    axes:      Axis[]
    resources: ResourceLedger
    statuses:  Status[]          // {id, sourceId, untilSec?}
    actions:   Action[]
    members:   Member[]          // {ref, role}
    relations: Relation[]
    footprint: Footprint | null
    meta:      { secret: boolean; threadIds: string[] }
  }
  cadence: Tempo
}
// SlotSpec[kind] = схема + подписи + иконка + render + derive## Что это закрывает в репозитории

- **Один instantiate(refId, kind).** Он снимает три открытых хвоста из ENTITIES.md: NPC справочника → Actor, организация → Faction, держава → фракция («в кампанию фракцией»).
- Существующие поля ложатся в слоты. Известность и влияние Faction, цены и опасность Location идут в оси и ресурсы без миграции смысла.
- Новые события. Нужны SUBJECT_MOVED и INTERACTION_*; всё остальное — уже есть.

## Риски

1. Ложная изоморфность. «HP города» — метафора, а не механика. Поэтому Vital и Axis открытые списки, а не фиксированные шесть характеристик.
2. Двойной учёт. Производный слой не хранится, а считается. Иначе состояние группы разойдётся с составом.
3. God-object. Слоты — данные и SlotSpec, а не ветвление if (kind === …) в компонентах. Ваше правило «компоненты тупые, state пропсами» это уже поддерживает.

Могу следующим шагом расписать SlotSpec для всех четырёх видов, derive()-правила rollup и схему Interaction в виде .md с Mermaid для Obsidian.
