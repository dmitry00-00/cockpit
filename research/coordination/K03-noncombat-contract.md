## 2. Предложения минимальных контрактов

Согласованы с инвариантами: event log как источник правды; компенсирующая отмена; предложение ≠ факт; секреты не доходят до игроков ни данными, ни DOM; навигация/черновики событиями не являются; `causeId` у дельты обязателен. Это предложения форм и обоснований, **без финального кода**; имена типов — рабочие.

### 2.(a) Встреча/разговор

**Суть.** Рабочая поверхность встречи: участники (акторы сессии), место (location в фокусе), история реплик/тем, сведения с учётом аудитории.

**UI-черновик.** Панель «Встреча» рядом с карточкой NPC: список участников (чипы актёров), место = текущий фокус места, лента тем/реплик. Тема выбирается из справочника/свободным текстом; «сказать партии» — флажок аудитории. Ничего в лог не пишет, пока мастер не подтвердил сведение.

**Контракт (минимум — без новых типов).**
- Начатый разговор и черновик реплики — состояние вида (как черновик TimeStepReview), событиями не являются: Д16 «начатый разговор… сам не меняет мир», CLAUDE.md «навигация, оверлеи… событиями не являются».
- Подтверждённые сведения — существующее `KNOWLEDGE_REVEALED` (`src/engine/events.ts:200-208`): `ref` на сущность мира, факт снимком, `by`, `check`. Для сведений «словами NPC» (не строка паспорта) — `NOTE_ADDED` с `visible: true` и `threadIds` (`events.ts:86`): запись игрокам, привязка к нитям есть.
- Связь с местом/нитями — готовая: `NoteAdded.threadIds/scale`, `delta.threadIds`, каскады по `causeId` (`src/engine/journal.ts:511-547`).

**Пробел, который стоит закрыть одним полем.** Аудитория сведения сейчас вся-или-никого: `KnowledgeRevealed.by` — один актёр, а «кто именно услышал» не хранится. Предложение: опциональное `heardBy: readonly string[]` (id PC) в `KnowledgeRevealed` — без него «сведения с учётом аудитории» живут только в пересказе мастера. Решение и миграция старых логов — за Codex (поле опционально, старые события реплеятся без него; валидация — id из `state.party`).

**Опционально позже.** Типизированный след встречи `CONVERSATION_RECORDED { participants, locationId, topicId?, atSec }` — только если владельцу нужен журнальный след самой встречи, а не её сведений. Сейчас это закрывается заметкой/знанием — предлагаю не плодить тип.

### 2.(b) Просьбы / Influence

**Суть.** Опора на существующее правило SRD 5.2.1, а не новое: навыки, Сл `max(15, INT)`, три отношения, animal-only, 24 часа — всё уже в `INFLUENCE_RULE` и валидаторе (`src/rules/srd/influence.ts:5-19`, `src/engine/reduce.ts:471-496`).

**Что менять (минимум).**
1. `NPC_SOCIAL_UPDATED` — расширить `kind` значениями `'gift' | 'insult'` с полем `lastGiftAtSec?` в `NpcSocialState` (по образцу `failedRequests`, но одна секунда на NPC): подарок/оскорбление — применения раз в десятидневку (правило стола: `research/game-mechanics.md:303,606`; эталон PF1 — раз в уровень, для стола медленно — там же). Валидация: `time.sec ≥ lastGiftAtSec + TEMPO_SECONDS.tenday` (`src/engine/events.ts:32`); отношение SRD и PF1-счёт этим не меняются (как сейчас для `attitude`, `reduce.ts:460-464`).
2. Журнал: запись секретна по аналогии с `kind: 'influence'` (`src/engine/journal.ts:376-378`) — игроки не видят ни проверку, ни блокировку.
3. Текст исхода — в `note`, как сейчас (`DeskPage.tsx:1002`).

**Что сознательно НЕ предлагаем.** Автоматическую смену отношения от успеха/подарка: Д12 зафиксировала «успех не меняет отношение автоматически» (TASKS.md:60), а PF1-счёт у нас ручной (TASKS.md:60, `reduce.ts:465-470`). Меняет отношение решение мастера существующим `kind: 'attitude'` — обратимо и секретно.

**Открыто владельцу (не решается кодом):** влияет ли подарок на PF1-счёт (PF1: Diplomacy против Сл = текущий счёт, успех +1/+2 — `research/game-mechanics.md:284-285`) при ручном счёте; явный тип связи PF1; стартовый Cha-мод спутника. Пока не решено — подарок только пишется в журнал мастера, числа не трогает.

### 2.(c) Предложение сделки (черновик ≠ покупка)

**Суть.** Мастер собирает сделку: продавец, покупатель, вещи/количество, валюта, цена и её источник, место хранения, видимые остатки. Просмотр и правка черновика мир не меняют; кнопка «Предложить» фиксирует версию черновика.

**UI-черновик.** В панели встречи: строки «отдаёт / получает» (сторона — PC, NPC-актёр, партия, место хранения), выбор вещи из SRD (`content/srd/equipment.json`), количество, цена с подписью источника («цена места: индекс 115 к базе SRD, Neverwinter, 15 Mirtul 1492 DR»). Рядом — остатки обеих сторон (кошелёк, запас вещи у продавца). Черновик редактируется свободно; «Предложить» — одна кнопка; после неё правка = новая версия того же предложения.

**Контракт (по образцу WorldDelta, известной командам).**
- `TRADE_PROPOSED { deal: TradeDeal }` — журнал: false, необратимо (как `WORLD_DELTA_PROPOSED`, `src/engine/events.ts:291`): предложение рождается только `pending`, без `patch` мира.
- `TradeDeal`: `id`, `version`, `seller: PartyRef`, `buyer: PartyRef`, `lines: { itemId, qty, side }[]` (side — кто отдаёт), `price: { amount, unit }`, `priceSource: { kind: 'market', locationId, index, atSec } | { kind: 'manual' }`, `fromStorage`, `toStorage`, `status: 'pending'|'accepted'|'rejected'|'withdrawn'`, `causeId`, `atSec`. Состояние: `State.deals: Record<string, TradeDeal>` (аналог `deltas`).
- Правка черновика после фиксации — `TRADE_AMENDED { dealId, version, deal }` с `version + 1` (новая версия отменяет прежнюю компенсацией), или проще: «предложить заново» новым `TRADE_PROPOSED` со `supersedes`. Решение Codex; важно одно: у предложения есть монотонный `version`.
- `TRADE_REJECTED / TRADE_WITHDRAWN { dealId }` — закрывают без изменения вещей/денег; решённое повторно не решается (как `reduce.ts:344-346`).

**Почему предложение в логе, а не в состоянии вида.** (1) «Устаревшее предложение» проверяется версией при подтверждении — нужен адресуемый объект; (2) два окна/два участника видят одно предложение; (3) undo/replay одинаковы для всех. Навигационного здесь ничего нет: предложение — обязательство между сторонами.

**Цена — только из данных.** Источник цены для покупки у торговца: индекс места (`priceRowOf`, `src/campaign/pulse.ts:92-105`) × база вещи. База в данных есть только строкой `cost` SRD. Курс cp/sp/gp/pp и цена продажи открытым источником в проекте не подтверждены — до решения (§6) ручной ввод цены с пометкой `priceSource: 'manual'` не запрещается, но подпись в UI обязана говорить «правило стола». Выдумывать курс/процент скупки нельзя.

### 2.(d) Подтверждённый обмен

**Суть.** Одна проверенная операция: атомарно меняет обе стороны; отрицательные остатки, дубликаты и устаревшие условия запрещены на входе; undo/replay/reload — следом одного события.

**Контракт.**
- `TRADE_COMPLETED { dealId, version, terms: DealTerms (снимок) , result: { wallets/items per side, before→after } }` — журнал: true, секрет: false (игроки видят свершившуюся сделку; условия — итоговые, Д16 «перед подтверждением видны итоговые условия»).
- Валидация (зеркалит стиль `reduce.ts`): обе стороны существуют и не выбыли; каждая строка вещей — `qty > 0` целое, без повторов `itemId` на сторону; у продавца вещей и у покупателя денег хватает (`amount > 0`, остаток ≥ 0 после списания); `deal.status === 'pending'`; `version` предложения совпал с принимаемым (иначе `EngineError('предложение устарело')`); если `priceSource: 'market'` — пересчитанный индекс места совпал со снимком сделки (иначе «цена устарела — обновите предложение»).
- Применение и след: один `Effect` `{ kind: 'trade', sides: [{ party, before, after }] }` — обе стороны снимком; `invert` меняет местами до/после; компенсация `TRADE_COMPLETED` с `undoes` восстанавливает обе стороны разом (механика готова: `src/engine/log.ts:97-112`, `src/engine/reduce.ts:1257-1290`).
- Подтверждение закрывает сделку (`status: 'accepted'` тем же событием), повторное принятие невозможно.

**Почему одно событие, а не пары ITEM_LOST/ITEM_GAINED.** «Деньги/вещи передаются одной проверенной операцией» (TASKS.md:64): пара событий даёт частичное применение при отказе второго и двойную запись журнала; один след — одна отмена. События вещей E7 (`ITEM_GAINED/ITEM_LOST/ROADMAP.md:264-269`) остаются для **односторонних** изменений (нашли, потеряли, съели); обмен — отдельный тип.

**Зависимость.** Требует модели вещей/кошелька из E7 (§5): без поля «у кого что лежит» валидировать нечего.

### 2.(e) Услуги, задания, подарки

**Суть.** Услуга/задание — обязательство NPC/партии, связанное с нитями и журналом; подарок — применение с лимитом раз в десятидневку. Явное отличие открытого правила от правила стола — в данных и в подписях.

**Контракт.**
- Услуга/задание — существующие средства, новых типов не нужно: открытая нить (`WORLD_DELTA_ACCEPTED` с патчем `newThread`, `src/engine/state.ts:162-163`) или заметка с `threadIds` для коротких поручений. Цена услуги, если есть, — та же сделка (§2.c/2.d) с `priceSource: 'manual'` и пометкой источника правила.
- Правило услуг: открытый кандидат — Black Flag (услуги по сословию, CC BY 4.0, `research/game-mechanics.md:430`), но прайс в проект не импортирован — до решения владельца услуги фиксируются ценой руками мастера с пометкой «правило стола». Текст из закрытых книг не берём.
- Подарок/оскорбление — §2.(b): `NPC_SOCIAL_UPDATED kind: 'gift'|'insult'`, лимит `TENDAY` от мирового времени. На карточке подарка — строка источника: «лимит раз в десятидневку — правило стола; эталон PF1 UC — раз в уровень (OGL)» (`research/game-mechanics.md:149,303`).
- Каждая форма обязана показывать слой правила: открытое правило — с источником/редакцией (как `INFLUENCE_RULE.source`, `src/rules/srd/influence.ts:6-9`), правило стола — с пометкой «правило стола» (как `KNOWLEDGE_RULE`, `src/campaign/knowledge.ts:20`). Фильтр «только SRD» (`CLAUDE.md` «Механика») сохраняется.

### 2.(f) Личное имущество / общая партия / лагерь / транспорт (стык с Д17)

**Суть.** У каждой вещи — количество и место хранения; перенос не дублирует вещь и сохраняет владельца; вес/вместимость — только при данных и правиле (Д17, TASKS.md:78).

**Что сейчас.** Личное: `sheet.equipment` (`state.ts:77-78`) — статика сида. Общее: `state.supply` (`state.ts:345-346`) — абстракция припасов, не вещи. Лагерь/транспорт: отсутствуют.

**Контракт (общая основа с E7/Д17 — предложение Codex'у как рамка).**
- Хранилище: `StorageRef = { kind: 'actor', id } | { kind: 'party' } | { kind: 'camp' } | { kind: 'transport', id }`. Вещь живёт в строке `{ storage, itemId, qty }`; владелец — свойство строки/хранилища, а не копии вещи (Д17: «переносы не дублируют вещь»).
- События E7: `ITEM_GAINED { storage, itemId, qty, reason }`, `ITEM_LOST { storage, itemId, qty, reason }` — решение владельца есть (`ROADMAP.md:264-269,764`), форма настоящим документом не фиксируется; деньги — вещи-«монеты» тем же путём (`ROADMAP.md:269`).
- Перенос между хранилищами: `ITEM_MOVED { itemId, qty, from, to }` — одна вещь, владелец сохраняется (критерий Д17, TASKS.md:78). Undo следом одной строки.
- Кошелёк: хранилище вещей-монет; баланс — производная строк, не отдельное число (иначе два факта о деньгах). Это следствие решения «деньги — ITEM_GAINED с id монеты» (`ROADMAP.md:269`).
- Вес/вместимость: показывать только когда есть и данные (вес есть в `content/srd/equipment.json`), и поддержанное правило. Открытое правило SRD 5.1 несения (STR×15) в проект не импортировано — вопрос владельцу (§6); до ответа — не считать и не показывать, как требует Д17.
- Для Д16 минимально достаточно: `actor` + `party` (+ монеты). `camp/transport` — этап Д17, блокирует только груз повозки, не базовую торговлю.

## 3. Сквозные пользовательские сценарии (10)

Сквозная цепочка Д16 (TASKS.md:71): поговорить → узнать/договориться → предложить сделку → подтвердить обмен → увидеть результат → отменить → восстановить после перезагрузки.

1. **Разговор и сведение.** Мастер открывает встречу с NPC-актёром в Neverwinter, ведёт тему «пропавший караван». Ничего не пишется в лог, пока он не подтверждает: «партия узнала» → `KNOWLEDGE_REVEALED` по нити каравана; фраза NPC уходит игрокам через `NOTE_ADDED visible: true` с той же нитью. В журнале — каскад «нить → сведение».
2. **Аудитория.** Сведение подтверждено только с `heardBy: [bo, lyra]`. На столе игроков сведение видно; у персонажей вне списка в партийной тетради пометка, кто присутствовал. (Требует поля из §2.a.)
3. **Просьба по SRD.** На карточке NPC мастер выбирает Bo, Убеждение, просьбу «проводите до тракта». Скрытый бросок, Сл `max(15, INT)`, отношение Indifferent. Успех: журнальная секретная запись «выполнена»; отношение само не меняется.
4. **Блокировка 24 часа.** Провал той же просьбы тем же навыком: кнопка гаснет с подписью «можно через N ч»; мастер продвигает время на сутки (`TIME_ADVANCED`) — просьба снова доступна. Ctrl+Z на шаге времени возвращает и блокировку.
5. **Подарок.** Мастер отмечает подарок спутнику: запись `kind: 'gift'`, повтор в той же десятидневке запрещён валидацией; после `+1 tenday` времени — снова доступен. Числа отношения не меняются (до решения владельца).
6. **Черновик сделки не покупка.** Мастер собирает сделку: продавец — торговец-актёр, покупатель — Korrin, 1 × «Healing Potion», цена из индекса Neverwinter (115 к базе), оплата из кошелька Korrin, вещь — в его снаряжение. Меняет количество на 2, смотрит остатки, закрывает черновик — в логе пусто, мир не изменился.
7. **Предложение → подтверждение.** «Предложить» фиксирует версию 1. Мастер снова открывает сделку, меняет количество на 1 — версия 2. Подтверждает версию 2: одно событие `TRADE_COMPLETED`; журнал у всех: «Korrin купил Healing Potion у … за … (остаток …)»; в снаряжении Korrin +1, в кошельке −цена, у продавца наоборот.
8. **Защита от устаревшего.** Снимок `priceSource` фиксирует и общий индекс места (`pricePercent`), и товарную надбавку на момент предложения. Пока сделка висела, мастер принял патч цены этого места → пересчёт индекса не совпал со снимком → «цена устарела», подтверждение отклонено валидацией, предлагается обновить черновик. Нехватка денег/товара → то же, мир не тронут (событие в лог не попало).
9. **Undo и reload.** Ctrl+Z на сделке: обе стороны возвращены одной компенсацией, журнал пишет «Отменено: …». Повтор (Ctrl+Shift+Z) применяет снова — только если остатки позволяют (валидация повтора следом). Сохранение файла сессии, загрузка: лог реплеится, сделка и вещи на местах.
10. **Секреты не текут.** В режиме «глазами игроков»: панель встречи с блокировками Influence, секретные записи социума и дельты отсутствуют (`filterJournal`, `journal.ts:491-500`); сделка видна только как совершившийся факт; скрытый бросок отсутствует. Импортированный торговец (Foundry) — лишь черновая запись (`ImportedContent`, `state.ts:293-304`), пока мастер не соберёт его актёром типизированным путём.

Дополнительные сценарии границ: продажа чужой вещи (§4, проверка 3), одновременные сделки (проверка 2), перенос вещи PC → общий запас и обратно без дублей (Д17, `ITEM_MOVED`).

## 4. Угрозы целостности/секретности и приёмочные проверки

| # | Угроза | Проверка приёмки (как ловим) |
|---|---|---|
| 1 | Отрицательные остатки (деньги/вещи) | Валидация `TRADE_COMPLETED`: списание ≤ остатка по обеим сторонам до применения (`validate` до записи, как `SUPPLY_CHANGED` `reduce.ts:367-377`); юнит-тест «купить за больше, чем есть» → `EngineError`, состояние неизменно, в лог пусто |
| 2 | Гонка двух сделок за одни деньги/вещи | Каждая сделка валидируется против текущего состояния; вторая подряд падает на остатках; две копии UI одного черновика расходятся по `version` — принимается только свежая; тест двух dispatch подряд |
| 3 | Продажа чужой/несуществующей вещи | Строка сделки указывает `storage` и `itemId`; валидация: хранилище существует, строка есть, `qty ≥ списанию`; `from`/`to` в `ITEM_MOVED` совпадают с фактическим местом вещи; тест «передать вещь из чужого снаряжения» → ошибка |
| 4 | Устаревшая цена/условия | `priceSource.market`: пересчёт индекса места на момент принятия ≠ снимку → `EngineError('цена устарела')`; `version` предложения ≠ актуальной → отказ; тест: изменить индекс места патчем между предложением и принятием |
| 5 | Дубликаты и нулевые строки | Уникальность `itemId` на сторону, целые `qty > 0`, цена `> 0`; пустая сделка не пишется; тесты повторов строк |
| 6 | Двойное принятие одного предложения | `deal.status` меняется тем же событием; повторное принятие → «уже решено» (по образцу `reduce.ts:344-346`); undo сделки возвращает статус предложения в `pending`, вещи — по следу; повторное undo невозможно (одна компенсация) |
| 7 | Утечка секретов NPC в режим игроков | `NPC_SOCIAL_UPDATED` (включая gift) — `secret: true` в журнале (`journal.ts:376-378`); панель социума рендерится только при `dmView` (`bodies.tsx:388`); скрытые броски — `hidden`; DOM-тест стол игроков: нет ни записей, ни атрибутов с DC/блокировками; e2e-прогон сценария 10 |
| 8 | Импорт как актёр | Импортированная запись не продаёт и не покупает, пока не стала актёром через типизированный путь (CLAUDE.md «Состояние»); валидация сторон сделки — только существующие не выбывшие актёры/хранилища; тест: `deal.seller = importedContentId` → ошибка |
| 9 | Неатомарность обмена | Один след `{kind:'trade', sides[before,after]}`; отмена восстанавливает обе стороны разом (`log.ts:97-112`); тест: отмена после частичного внешнего изменения чужой стороны ведёт себя предсказуемо (след побеждает, как у `hp`); replay сохранённого лога воспроизводит обмен без повторной валидации цен (валидируется след, не экономика) |
| 10 | Потеря после reload | Сохранить файл сессии после сделки и undo, загрузить: реплей без ошибок (`log.ts:121-133`), состояние вещей/денег равно досохранённому; `EventLog.check` зелёный |
| 11 | Cooldown от стены вместо мира | Блокировки Influence/подарка считаются от `state.time.sec`; тест: откат TIME_ADVANCED возвращает блокировку; перевод часов вперёд снимает её — без `Date.now()` в домене |
| 12 | Предложение, похожее на свершившийся факт | `TRADE_PROPOSED` — `journal: false`, пульсации/подписи «ждёт решения» (по образцу `glow-sim`, CLAUDE.md «Правила экрана»); тест: до принятия остатки в UI старые, pending-чип виден |

## 5. Порядок реализации (этапы и зависимости)

**Этап 0 — разговор на существующих событиях (блокируется ничем).**
Панель встречи как состояние вида; сведения через `KNOWLEDGE_REVEALED` (+опционально `heardBy`, §2.a), слова NPC через `NOTE_ADDED visible`. Расширение Д13, новых типов нет. **Не блокируется** и не блокирует торговлю, но даёт «поговорить → узнать» из сценариев 1–2.

**Этап 1 — E7: вещи и кошельки (блокирует торговлю и Д17-инвентарь).**
Типы `ITEM_GAINED/ITEM_LOST` (+решение по форме хранилищ и монет, §2.f), переход `sheet.equipment` на event-sourced модель или зеркалирование; проекции веса/вместимости — только после ответа владельца (§6). Зависит от приёмки R02 контракта; решение владельца по событиям уже есть (`ROADMAP.md:764`). До этого — **только показ данных сида и редактора** (`ROADMAP.md:269`), сделки не строить.

**Этап 2 — социальные применения (блокируется ничего, часть Д12).**
`kind: 'gift'|'insult'` с лимитом десятидневки (§2.b). Зависит только от существующего `NPC_SOCIAL_UPDATED`. Можно параллельно с этапом 1.

**Этап 3 — сделки (блокируется этапом 1 и данными рынка С3 — те готовы).**
`TRADE_PROPOSED/AMENDED/REJECTED/WITHDRAWN/COMPLETED` (§2.c/2.d), валидации §4, журнал и проекция игроков. Цены места берутся из существующих `priceRowOf`/патчей (`src/campaign/pulse.ts:92-105`); интеграция с С3 — только чтение индекса, запасы мира сделка не трогает (запасы — домен симуляции; см. вопрос 7 в §6).

**Этап 4 — услуги и задания.**
Нити + заметки + сделки как цена; слой правил и пометки источников (§2.e). Зависит от этапа 3, если услуга платная.

**Этап 5 — пространство партии (стык Д17, частично блокируется этапом 1).**
`ITEM_MOVED`, хранилища `party/camp/transport`, раскладка Д17 (K01/R01). Торговля не блокируется: ей хватает `actor/party`.

Порядок выбран так, чтобы самая рискованная часть (атомарный обмен) шла после стабилизации модели вещей, а разговор/просьбы давали ценность немедленно на существующих типах. Никакой миграции состояния в рамках этого документа не предполагается; старые логи реплеятся без новых полей (все предложения — опциональные поля/новые типы).
