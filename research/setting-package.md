## 0. Коротко

1. **Сеттинг — пакет данных без кода. Правила — картридж (код и данные). Кампания — свой пакет поверх обоих.** Так же устроен Foundry VTT: system, module и world. Ядро знает только общие виды сущностей, время в секундах, девять рангов лестницы и событийный лог. Календарь, линзы редакций, подписи и виды уровней лестницы, корневые места и все справочники приходят из манифеста пакета.
2. **Лицензия и выход с машины записаны машиночитаемо в каждом слое (файле), а у отдельной записи — только если она строже слоя.** Уровней выхода три: `open` (можно куда угодно), `table` (только стол владельца), `internal` (только эта машина: разработка и тесты). Производное наследует самое строгое из входов. CC BY-SA — всегда `internal` (решение пользователя 30.10.2026).
3. **Флаг держат не договорённости, а три механизма.** Первый — физическое разделение: пакеты не-`open` лежат вне публичного репозитория. Второй — метка-канарейка и отпечатки текстов. Третий — проверка на каждом выходе, которая падает с кодом и списком нарушений.
4. **Главная находка — выход уже открыт.** Репозиторий `dmitry00-00/cockpit` на GitHub **публичный**. В локальном `main` лежат 32 непушнутых коммита, из них в 9 — данные FR Wiki под CC BY-SA. Первый же `git push`, который ROADMAP 0.1 и §15 ставят первой строкой, опубликует их. Кроме того, на GitHub с 21.09 уже лежит то, что по собственной разметке проекта — «только для своего стола»: переводы книг WotC в компендиуме, исходные xlsx и фанатские растры карт. Подробности — §5.1.

## 1. Вопрос

Что относится к общему ядру и что — к пакету сеттинга, чтобы:

- Forgotten Realms, который сегодня зашит в код, стал пакетом №1;
- следующий сеттинг подключался без правки ядра (TASKS П3, «готово, когда»).

От ответа зависят:

- П3 — другие сеттинги;
- П4 и ИС1–ИС3 — импорт сеттингов;
- П8 — редактор мира поверх пакета;
- П9 — магазин материалов;
- П5 и ПР11 — конвертер редакций и картридж правил.

Список целей — около 44 сеттингов, игровых и литературных, в том числе космических. Космические проверяют уровни «система» и «планета», которые у FR почти пусты.

Жёсткое условие (решение пользователя 30.10.2026; ROADMAP §16, SOURCES «Решения»): материал под CC BY-SA используется **только внутри — для разработки и тестирования**. Вовне — никогда и нигде, даже для внешнего тестирования. Поэтому формат несёт происхождение и право на выход у каждого слоя и записи. У каждого пути, которым данные покидают машину, стоит проверка.

Вывод из сравнения:

- Никто из образцов не несёт в данных флаг «не выпускать с машины». Foundry и FG держат права в раздаче (магазин, ключи), 5etools не несёт лицензии вовсе, Open5e несёт её у документа.
- Наш случай строже: запрет касается в первую очередь своей машины и своих выходов. Поэтому правило выхода нужно ввести самим, на уровне слоя, по образцу Open5e. Соблюдать его будут собственные проверки на выходах.
- Граница FG `db.xml` / `client.xml` подсказывает, что экраны игроков — отдельный выход со своим решением.

## 4. Предлагаемый формат

### 4.1. Четыре вида пакетов

| Вид | Что внутри | Код? | Пример |
|---|---|---|---|
| `rules` — картридж правил | атомы правил (состояния, навыки, кости), вывод листа, монстры, заклинания, предметы | **да** — модуль ядра в `src/rules/<id>/` плюс данные | `dnd5e-2014` (сегодняшние `src/rules/srd` и `content/srd`), `a5e` (поход, монстры), `bf` |
| `setting` — сеттинг | календарь, линзы канона, лестница, корневые места, справочники мира, карты, хронология, привязки к правилам | **нет** — только данные и манифест | `fr` (пакет №1), позже `planetos` |
| `shared` — общий слой нескольких сеттингов | например, Великое колесо и Sigil, которые D&D-сеттинги делят между собой | нет | `dnd-multiverse` (сегодня — данные FR Wiki, значит `internal`) |
| `campaign` — кампания | эпоха (sec 0), сид (партия, ростер, мир §13), слой правок канона (П8) | нет | `neverwinter-demo` |

Сеттинг — только данные. Это главное решение формата. Второй сеттинг тогда подключается без кода по построению: всё, чего сеттингу не хватает, — либо общий вид карточки (`EntityView` уже общий), либо пробел ядра, который закрывается один раз для всех сеттингов. Новые механики — дело картриджа правил, и это код (как system в Foundry).

```jsonc
  "rules": { "systems": ["dnd5e-2014", "a5e"], "default": "dnd5e-2014" },
  "time":   { "calendar": "calendar.json", "lenses": "lenses.json" },
  "ladder": "ladder.json",
  "maps":   ["maps/toril.json", "maps/neverwinter.json"],
  "kinds":  { "kingdom": { "labelRu": "Держава" } },   // подписи общих видов в этом сеттинге
  "layers": [
    {
      "id": "deities", "path": "cosmos/deities.json", "kinds": ["deity", "pantheon"],
      "license": "CC-BY-SA-3.0",                       // SPDX; несколько — выражением SPDX
      "distribution": "internal",                      // open | table | internal
      "decision": "SOURCES.md §2 · решение пользователя 30.10.2026",
      "attribution": "Forgotten Realms Wiki (forgottenrealms.fandom.com), авторы статей; CC BY-SA 3.0",

  "canary": "dmck-fr-7f3a…"                            // случайная метка пакета не-open (§5)
}
```

Правила манифеста:

- **Запись без слоя не существует.** Каждый файл пакета указан ровно в одном слое. Тест падает на файл вне манифеста и на слой без `license` и `distribution`. Это прямое продолжение правила CLAUDE.md «запись без источника не существует».
- **Производное наследует самое строгое.** `distribution` слоя не мягче, чем у любого слоя из `derivedFrom`. Порядок строгости: `internal` > `table` > `open`. Пример: русские карточки L3 — пересказ локальной моделью статей вики и описаний GIS, значит `internal`. Подписи схемы — полигоны GIS (CC BY-SA 4.0) на пикселях растра HandsomeRob (стол), значит `internal`.
- **Запись строже слоя — своим полем.** У отдельной записи могут стоять `license` и `distribution`, но только строже слоя. Пример: в открытом слое — одна запись, переписанная из книги, `table`. Мягче слоя запись быть не может — тест.
- **Копия значения несёт происхождение.** Если значение справочника скопировано в состояние или файл (имя, факт), рядом стоит `from: "fr/deity:lathander"`. Выход считает строгость по этим ссылкам (§5.3).

Соответствие категориям SOURCES:

| SOURCES | `distribution` | Примеры сегодня |
|---|---|---|
| **берём**, лицензия без SA (CC BY 4.0, OGL, CC0) | `open` | SRD 5.1, A5E, Black Flag |
| **берём**, CC BY-SA, FDL — решение 30.10 | `internal` | FR Wiki, Spelljammer Wiki, Toril GIS (CC BY-SA 4.0) |
| **факты** | по источнику фактов; если факты из SA-источника — `internal` (вопрос 8) | пары AideDD (только сверка, в данные не идут) |
| **стол** | `table` | растр и тайлы HandsomeRob, план Neverwinter (© WotC), переводы книг в компендиуме (`source: book` — по `meta.license` самого файла «только для своего стола») |
| **смотрим**, **купить**, **нет** | в пакет не попадает | — |

### 4.3. Ссылки

- Внутри пакета остаётся сегодняшний вид `вид:id`. Полная форма — `пакет/вид:id`, например `fr/deity:selune` или `dnd5e-2014/condition:prone`.
- Неполная ссылка разрешается по цепочке «кампания → её сеттинг → его `requires` → картридж правил». Поэтому сохранённые логи и сид (`organization:zhentarim`, `place:<uuid>`) читаются без миграции, а кампания связана ровно с одним сеттингом.
- Полная форма нужна там, где сеттинги встречаются: Spelljammer, Planescape, общий Sigil.
- `parseRef` учится необязательному `пакет/`. `PACK_OF` и `LOADERS` строятся из манифестов, а не из закрытых таблиц кода.
- Список видов делится на два: ядро — понятные коду виды (`place`, `person`, `organization`, `kingdom`, `deity`, `pantheon`, `plane`, `body` и правила); виды пакета (`kinds` в манифесте) — например, `sphere` у FR или `hyperlane` у Star Wars. Вид пакета рисуется общей карточкой `EntityView` из полей записи: факты, секции, ссылки, группы. Новый вид не требует кода, пока ему не нужна своя механика.
- id стабильны по источнику: слаг статьи вики, UUID GIS, ключ SRD. Переименования статей вики идут в слой `ids.json` пакета: старый id → новый (перенаправления дампа уже читаются в `import-deities.py` **[код]**).

Для общего runtime-проектора справочных записей пакет может объявить JSON-слой со стандартной обёрткой `cockpit.entity-layer/1`:

```json
{
  "format": "cockpit.entity-layer/1",
  "kind": "place",
  "entities": [
    {
      "ref": "place:harbor-city",
      "kind": "place",
      "name": "Harbor City",
      "source": { "kind": "package", "cite": "Пакет setting-name", "license": "CC-BY-4.0" },
      "facts": [], "sections": [], "links": []
    }
  ]
}
```

Слой должен объявлять тот же `kind`; у записей должны быть уникальные ID, согласованные с `ref`, и валидные поля `EntityView`. Проектор читает только эту явно версионированную форму. Неизвестные и существующие доменные JSON-слои остаются ответственностью своих загрузчиков. Сейчас общий проектор принимает виды из `REFERENCE_KINDS`; динамические виды пакета и их механики требуют отдельного runtime-контракта.

### 4.4. Время: ядро и календарь

**Ядро** держит:

- целые секунды `sec` от эпохи кампании;
- `SECONDS_PER_DAY = 86400` (сутки по стенке — общие; местные сутки планет — флавор, вопрос 13);
- `TIME_ADVANCED` и темпы.

Лог хранит только `worldSec`, поэтому от календаря не зависит **[код]** (`engine/events.ts`, сид — `worldSec`). Эпоха (что такое sec 0) — поле **кампании**, а не сеттинга: иначе правка календаря сдвинет все сохранённые логи.

**Календарь** — данные сеттинга (`calendar.json`), по модели Calendarium и Kanka:

```jsonc
{
  "id": "harptos", "kind": "months",              // months | counter (Planetos: «день N») | gregorian
  "yearSuffix": "DR", "yearZero": true,
  "months":  [{ "id": "hammer", "name": "Hammer", "days": 30 }, …],
  "intercalary": [{ "id": "midwinter", "name": "Midwinter", "after": "hammer", "days": 1 }, …,
                  { "id": "shieldmeet", "name": "Shieldmeet", "after": "midsummer", "days": 1,
                    "leap": [{ "every": 4, "offset": 0 }] }],   // григорианский: 4 / не 100 / 400
  "week": { "name": "десятидневка", "days": 10 },
  "dayPhases": [{ "id": "morning", "from": 5 }, …],              // сегодня — dayPhase в коде
  "seasons": [{ "id": "winter", "from": "hammer" }, …],
  "solar": { "equinoxSpring": { "month": "ches", "day": 19 }, … },   // святые дни ссылаются
  "moons": [{ "id": "selune", "ref": "body:selune", "cycleDays": 30,
              "fullAt": { "year": 1492, "month": "mirtul", "day": 18 } }],
  "yearNames": { "layer": "roll-of-years" }                       // имена лет — слой справочника
}
```

- `calendar.ts` становится движком над этой моделью. Харптос сегодня — частный случай: 12×30, 5 вставных дней, ещё один раз в 4 года, одна луна. Переход проверяет «золотой» тест: на отрезке ±3000 лет вокруг 1492 DR старый и новый код дают одинаковые `harptos(sec)` и `secOf`.
- Святые дни и любые правила дат ссылаются на **id** слотов календаря и лун (`"festival": "midsummer"`, `"moon": "selune"`), а не на английские имена. Так их проверяет схема.
- Строки «Selûne растёт» и суффикс «DR» в `CelestialBar`, `pulse`, `scene`, `simulation`, `WorldMap`, `knowledge` берутся из календаря.
- Сеттингу с несколькими лунами — массив `moons`: Krynn — три, Eberron — двенадцать [память]. Полоса часов показывает первую по порядку или ту, что в событии.

**Линзы канона** (`lenses.json`) — обобщение `era.ts`. Осей две, они не сводятся друг к другу:

1. **Редакция по году мира** — у FR это `3e` ≤ 1384, `4e` ≤ 1487, `5e` дальше:

   ```jsonc
   "editions": [
     { "id": "3e", "to": 1384, "fieldOrder": ["3e", "2e", "1e", ""], "cosmology": "tree" },
     { "id": "4e", "to": 1487, "fieldOrder": ["4e", "3e", "2e", "1e", ""] },
     { "id": "5e", "fieldOrder": ["5eR", "5e", "4e", "3e", "2e", "1e", ""], "cosmology": "wheel" }
   ]
   ```

   Тип `Era` становится строкой из пакета. `resolve(kind, id, era, year)` остаётся тем же.

2. **Непрерывность канона** (continuity) — линза мастера, не зависящая от года. Примеры: Star Wars Canon и Legends; книги и сериал у «Песни льда и пламени» и «Ведьмака»; игры и книги у Warhammer [память]. Запись или поле несёт `continuity`; кампания выбирает одну. У FR — одна непрерывность, поле пусто.

### 4.5. Лестница масштабов у сеттинга

Девять рангов ядра (`SCALE_LEVELS`) **остаются**: они записаны в логе (`NOTE_ADDED.scale`, `WorldDelta.scale`), и у каждого — темп часов. Сеттинг в `ladder.json` говорит, что значит каждый ранг:

```jsonc
{
  "roots": "ladder-roots.json",          // места верхних уровней: у FR — Колесо, Материальный, Realmspace, Toril, Faerûn
  "ranks": {
    "cosmology": { "labelRu": "Космология", "view": "wheel|tree" },   // вид — из набора видов ядра
    "plane":     { "labelRu": "План",       "view": "flowgraph" },
    "system":    { "labelRu": "Система",    "view": "orrery" },
    "planet":    { "labelRu": "Планета",    "view": "globe", "mask": "toril" },
    "continent": { "view": "map" }, "region": { "view": "map", "hexMiles": 6 },
    "settlement":{ "view": "map|plan" }, "building": { "view": "plan" }, "battle": { "view": "grid" }
  },
  "sublevels": { "region": [{ "id": "subregion", "labelRu": "Подрегион" }] }
}
```

- Виды уровня — закрытый набор ядра: `wheel`, `tree`, `flowgraph`, `orrery`, `globe`, `map`, `plan`, `grid`, `cards`. Сеттинг выбирает вид и даёт данные; код вида один на все сеттинги.
- Корневые места FR уезжают из сида кампании в пакет сеттинга. Сид кампании ссылается на них.
- `sublevels` — несколько именованных уровней внутри одного ранга. Это уже работает: подрегион Triboar Trail — того же ранга, что Sword Coast North (`ladder.ts`) **[код]**.

**Космические сеттинги на этой лестнице.** Наблюдение из кода: уровень «план» у FR рисует `FlowGraph` — граф течений флогистона между сферами с днями пути **[док]**. По устройству это граф межзвёздных путей: гиперпространственные трассы, ретрансляторы, звёздные врата. Поэтому ранг `plane` у научной фантастики — «пространство между системами», а `system` и `planet` — свои, полные.

| Сеттинг | cosmology | plane (граф путей) | system | planet | ниже |
|---|---|---|---|---|---|
| FR | Колесо / Древо | Материальный, флогистон — сферы и течения | Realmspace, планетарий | Toril, глобус | континент → … → бой |
| Star Wars [память] | Сила — скрыт или карточки | галактика: подуровни «область» (Core, Mid Rim, Outer Rim) → «сектор»; рёбра — гипертрассы | звёздная система, своя для каждой планеты | сотни планет | город, здание, бой |
| Mass Effect [память] | — | галактика → кластер; рёбра — ретрансляторы | система | планета | колония, корабль |
| StarCraft [память] | (Пустота) | сектор Копрулу | система | планета | — |
| EVE [веб] | — | регион → созвездие (подуровни); рёбра — звёздные врата; пространства known / wormhole / abyssal | солнечная система — свои координаты | планеты и луны, круговые орбиты | станция — «здание» |
| Warhammer 40k [память] | Варп — карточки | сегментум → сектор → субсектор | система | мир-улей | город-улей: поселение со своей глубокой вложенностью |
| Planetos (M11) | — | — | — | глобус по маске (уже есть) | континент → … |

Пробелы ядра, которые эта таблица называет:

1. Вид `orrery` (`Planetarium`) сегодня читает FR-специфичный `realmspace.ts`. Ему нужна общая модель тел: орбита, период, родитель. У EVE орбиты круговые [веб], так что та же простая модель годится.
2. `flowgraph` сегодня — течения флогистона. Ему нужна общая модель «узлы + рёбра с днями пути».
3. Сезоны и сутки — свойство **планеты**, а не сеттинга: у сеттинга с сотней планет `seasonOf` по месяцам ложен. Предлагается так: календарь сеттинга — общий счёт времени; сезоны, фазы суток и луны — у тела `body`. FR кладёт всё на Toril, и для него ничего не меняется.

### 4.6. Картридж правил и привязки

- Картридж правил = сегодняшние `src/rules/srd` + `content/srd` + `rules/compendium` (только записи `srd`) + `rules/a5e`. Его id — `dnd5e-2014`.
- Ось `gamesystem` по образцу Open5e: `5e-2014`, `5e-2024`, `a5e`.
- Отметка редакции у записи — как `edition` у 5etools.
- Сеттинг в `rules.systems` перечисляет совместимые картриджи.
- Всё, что связывает мир с механикой, лежит в слое привязок `bindings/<rulesId>/` пакета сеттинга. Пример: домены 5e богов FR → подклассы жреца (`domainSubclasses` в `cosmos/deities.ts` **[код]**). Это `system` у пакета компендиума Foundry.
- П5, конвертер редакций: картридж объявляет `converts: [{ from: "dnd35", to: "dnd5e-2014" }]`. Запись-результат несёт `converted: { from, lost: [...] }` — критерий TASKS П5. Подбирать редакции по году сеттинга картридж не обязан: это линза сеттинга (§4.4), отдельная от редакции правил стола (ПР11).
- Записи `book` компендиума — не картридж и не сеттинг, а отдельный пакет `owner-tables`, `distribution: table` (SOURCES: «стол»).

### 4.7. Правки канона (П8) и магазин (П9)

- **Правка канона — слоем кампании, без перезаписи.** Записи вида `{ "patch": "fr/kingdom:cormyr", "set": {...}, "hide": [...] }` — по образцу `_copy`/`_mod` у 5etools и `replaces` у FG. Своё место или держава — новая запись в пакете кампании с `distribution: open` (своё) — или строже, если она построена на внутреннем (наследование).
- Правки вне сессии — данные пакета кампании. Правки за столом — по-прежнему события лога (CLAUDE.md «Состояние»). Граница та же, что у ростера сида.
- **Магазин (П9) торгует только пакетами `open`**, у которых лицензия разрешает коммерцию. Поле `commercial: allowed | forbidden` выводится из SPDX (CC BY-NC — `forbidden`) и сверяется тестом. Пакет `internal` или `table` магазин не принимает по построению. Флаг `protected` у Foundry показывает, что защиту покупки держит раздача, а не формат. Для П9 это отдельное решение владельца.

### 5.2. Три механизма, на которых держатся проверки

1. **Физическое разделение — главный.** Пакеты `internal` и `table` лежат вне публичного репозитория: каталог `DM_PACKAGES_DIR` (по образцу уже существующего `DM_TILES_DIR`) или отдельный приватный репозиторий. Ядро грузит их через виртуальный модуль Vite `virtual:dm-packages`, который собирается из манифестов найденных пакетов. Без пакета FR стол поднимается на открытом демо-пакете. Тогда путь git закрыт устройством, а не проверкой.
2. **Метка и отпечатки.**
   - **Канарейка:** у каждого пакета не-`open` — случайная метка. Плагин сборки вписывает её в каждый кусок с данными пакета, импортёр — в шапку каждого файла слоя. Она ловит утечку файла или куска целиком.
   - **Отпечатки:** локальный индекс хэшей шинглов по 8 слов из текстовых полей слоёв не-`open` (`sections`, тексты событий, цитаты). Он ловит скопированные предложения: в тестах, документах, файлах сессии, страницах. Имена не хэшируются: имена — факты, и они есть в любом документе. Индекс — только хэши, он не материал, но лежит в `.cache/` вне git.
   - Сканер один на всех: `scripts/check-distribution.mjs <пути|-> --exit <имя>`. Выход ненулевой; печатает файл, метку или фрагмент, слой и решение из `decision`.
3. **Проверка на каждом выходе** (таблица ниже) зовёт сканер или строгость слоя и **падает с кодом**. Молчаливого пропуска нет.

## 8. Вопросы пользователю

1. **Экраны игроков за реальным столом** — LAN-планшет, второй монитор, проектор, трансляция удалённым игрокам. Можно ли показывать там материал `internal` (FR Wiki)? Считается ли живая сессия «тестированием»? Ответ определяет, нужна ли сборка `table` для LAN и чем `table` отличается от `internal` на практике. Предложение: `internal` — только экран мастера на этой машине; `table` (книги владельца, фанатские растры) — и на устройствах игроков за столом.
2. **Свои устройства и копии.** Вторая машина (Windows), планшет, внешний диск `/Volumes/внешний`, Time Machine, iCloud. Можно ли копировать на них пакеты `internal`?
3. **Агенты.** Всё, что агент читает, уходит в API модели. Это «внутри» (разработка) или выход? Сюда же — страницы-артефакты: запрещены для любого материала не-`open` (предлагаю — да, хуком)?
4. **Облачные LLM для разметки.** Запретить для данных вики полностью, проверкой в `llm-markup` и в шлюзе? Предлагаю — да.
5. **Уже опубликованное на GitHub:** переводы книг в компендиуме (`source: book`), два xlsx, растры `maps/abeir toril/` и `maps/ASOIAF/`. Варианты: сделать репозиторий приватным, переписать историю (`git filter-repo`) или оставить.
6. **Девять непушнутых коммитов с CC BY-SA.** Варианты: переписать историю до пуша (вынести `content/world`, `cosmos`, `chronology`, `toril-cards`) или пушить только в приватный удалённый репозиторий. Публичный `main` в нынешнем виде пушить нельзя.
7. **Производное.**
   - Координаты, снятые с фанатского растра HandsomeRob (`geo` мест, позиции справочника): факт, который мы измерили, или «стол»?
   - Русские пересказы L3 локальной моделью по статьям вики — наследуют `internal`?

   Предлагаю по самому строгому: координаты — `table`, L3 — `internal`.
8. **Только факты из вики** — имена, годы, связи «кто кому служит». Решение 30.10 касается «материала». Распространяется ли оно на факты, извлечённые из CC BY-SA? Это решает, может ли когда-нибудь существовать «фактовый» пакет FR `open`.
9. **Выгрузка слепка хроники** `canon-<год>-DR.json`: оставить с пометкой `.internal` или только в сборке разработки?
10. **Где живут пакеты не-`open`:** каталог `DM_PACKAGES_DIR` вне git, отдельный приватный репозиторий или зашифрованный каталог внутри (git-crypt)? Предлагаю каталог вне git плюс приватный репозиторий для его истории.
11. **Ссылки.** Принять форму `пакет/вид:id` с разрешением неполных по цепочке кампании, без миграции сохранённых логов?
12. **Виды.** Можно ли пакету объявлять свои виды сущностей, которые рисуются общей карточкой, — `sphere`, `hyperlane`? Подписи общих видов — по сеттингу («Держава» и «Империя» для `kingdom`)?
13. **Правила.** Сеттинги — только данные; другие системы правил (Cyberpunk, Shadowrun, Call of Cthulhu) — отдельные картриджи-код. Первая волна ИС — только сеттинги на правилах 5e?
14. **Пилот второго пакета.** Planetos (M11: маска и растр уже есть, календарь — счёт дней) или сразу пакет `open` (свой мир или общественное достояние), чтобы проверить путь наружу?
15. В списке TASKS — «evequest»: EverQuest или EVE Online? Вопрос уже стоит в TASKS. Для лестницы EVE полезнее: планетные уровни у неё заполнены данными SDE.

## 14. Content-root routing для FR-импортёров — 24.11.2026

Шесть FR-импортёров (`import-deities`, `import-organizations`, `import-people`, `import-chronology`, `import-chronology-articles`, `import-kingdoms`) принимают необязательный `--content-root` и также читают общий `DM_COCKPIT_CONTENT_ROOT`, чтобы helper-модули, загружаемые через `importlib`, видели тот же root. Без переопределения остаётся `<repo>/content`. Все найденные ими чтения и записи слоёв `content/**` идут через общий `scripts/content-paths.py`; script loader остаётся привязан к репозиторию.

Побочные локальные входы оформлены явно: `import-chronology-articles.py --classification-file` принимает редакторский файл классификаций, `import-kingdoms.py --gis-package` принимает GeoPackage, а `--skip-gis` запрещает прежний поиск GIS по корню checkout. Импортер организаций получает временный places JSONL аргументом профиля; скрытый `/Volumes/...` fallback задействуется только при прямом ручном запуске без файла. В профиле FR wiki-дамп помечен `outsideRepository`; runner проверяет исходный путь и `realpath`, поэтому отвергает файл из checkout, ссылку на файл внутри него и внутреннюю ссылку на внешний дамп.

Если оператор явно передал `--gis-package`, но `ogr2ogr` не найден, `import-kingdoms.py` теперь завершает этап ошибкой вместо тихого выпуска записей без GIS-связей. Когда профиль не передаёт GeoPackage и объявленно добавляет `--skip-gis`, прежний безопасный fallback остаётся явным и штатным.

Добавлен `scripts/setting-import-run.mjs`. Он проверяет профиль и входы до создания результата, требует пустую новую папку вне checkout, копирует объявленные `existing-layer` в корень пакета `content/`, переносит проверенный `packages/fr/package.json` в корень результата и запускает этапы последовательно из временного рабочего каталога. Профиль объявляет все исходные слои манифеста, в том числе копируемые без участия импортёров. GIS либо передаётся как явный optional input, либо отключается профилем. Перед и после каждого этапа runner сравнивает исходный `content/`, остальные existing-layer и манифест; изменения результата сверяет с `writes`/`alsoWrites`. В финале проверяет совпадение ID, что каждый слой манифеста существует как обычный файл, и что каждый файл/каталог `content/` покрыт слоем манифеста. Автоматической публикации в канонический пакет нет.

Статическая сверка пакета нашла 58 путей слоёв; все они теперь покрываются зарегистрированными копируемыми или генерируемыми артефактами профиля. Help и итоговая строка описывают полный package root: `package.json` и `content/`. `check-packages.mjs` по-прежнему валидирует checkout и генерирует индекс приложения; это не проверка/публикация собранного output.

Это пока реализация без прогона: внешний XML-дамп и GeoPackage через runner не запускали, тесты/typecheck/импортёры/планировщик не запускались. Статически проверены синтаксис runner/plan и покрытие 58 манифестных путей. IS2 остаётся открытой до реальной изолированной сборки и проверки пакета, общего профиля второго сеттинга и решения по ИС1. Скрипты всё ещё FR-специфичны; GIS-карта второго сеттинга не создаётся автоматически.

**Уточнение безопасности, 24.11:** `ensureSafeOutput()` сначала находит и канонизирует ближайшего существующего родителя, проверяет предполагаемое расположение и только затем создаёт отсутствующие каталоги. Канонизация допускает системный alias `/tmp` → `/private/tmp`, но отклоняет результат, если alias разрешается внутрь checkout. Отклонённый путь внутрь checkout не должен оставлять каталоги. Снимок этапов также учитывает директории: создание незаявленной пустой папки выявляется, а финальная проверка допускает только директории, которые являются родителями объявленного слоя. Пути слоёв манифеста проверяются как обычные файлы, так что пустая папка не может заменить `.json`/`.jsonl`. Проверки ограничились синтаксическим разбором и просмотром diff; runner, планировщик, импортёры и тесты не запускались.

**Внешний wiki-дамп, 24.11:** `packages/fr/import-profile.json` задаёт `outsideRepository: true` для обязательного входа `dump`; валидатор профиля разрешает эту политику только для `external-input`. Runner отказывает, если исходный путь либо canonical realpath находятся внутри checkout, и сохраняет для этапов canonical path. Тогда хэширование содержимого входа ещё не выполнялось; ограничение снято последующим уточнением ниже.

**Закрепление политики в схеме:** валидатор связывает `sources.wiki.dumpPath` с обязательным артефактом `external-input` и требует `outsideRepository: true`. Поэтому будущая правка профиля не сможет незаметно ослабить ограничение, просто сняв флаг с `dump` или подменив его внутренним путём.

**Целостность внешних входов, 24.11:** runner теперь снимает SHA-256 каждого переданного `external-input` потоком один раз перед сборкой и один раз после неё, даже если этап завершился ошибкой. Перед и после каждого этапа он сверяет лёгкие метаданные с исходной записью (канонический путь, тип/режим, размер, inode/device, число ссылок, mtime и ctime); это даёт раннюю атрибуцию изменившегося входа этапу, не перечитывая большой XML на каждом шаге. Хэширование использует поток и ограниченную память; оно дважды читает каждый переданный файл за запуск. Такое сравнение обнаруживает сохраняющееся изменение содержимого и обычные замены/перезаписи между проверками, но не предотвращает запись и не является OS-level изоляцией: краткое изменение с полным восстановлением исходных байтов и метаданных между проверками может остаться незамеченным. Обычные файловые снимки output/scratch/read-only слоёв также переведены на потоковое SHA-256. Точные затраты и границы: `research/setting-import-input-integrity-2026-11-24.md`.
