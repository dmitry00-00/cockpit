# БА27 — аудит сложных выборов и план завершения

Дата: 2026-11-03. Аудит read-only исходников текущей грязной рабочей копии. Код и генераторы не менялись; UI не запускался.

## Краткий вывод

Дерево `classPath` корректно сохраняет импортированные `levels`, `subclasses`, `options`, source и текст для просмотра. Но импортированные блоки `ClassOptionBlock` не являются общим контрактом выбора при повышении. Связь с `sheet.choices` сейчас проходит через отдельную SRD-ориентированную функцию `classChoicesOf` в `src/campaign/build.ts`: она по жёстко заданному имени извлекает только «Боевой стиль» и «Метамагию», плюс отдельные вручную описанные SRD-выборы. Большинство импортированных классовых и подклассовых блоков, в том числе выборы из книг, редактором создания персонажа и повышением не управляются.

Д8 сохраняет новые умения в `sheet.features`, но не добавляет выборы. `levelUpPreview` обнаруживает часть неподдержанных выборов эвристикой имени/текста и предупреждает, однако само умение уже попадает в лист как полученное. Нужен отдельный слой: общий source-aware каталог требований выбора, запись решения в листе с уровнем и источником, а механические эффекты включать лишь через явно реализованные и версионированные адаптеры.

## Что сейчас происходит

### Импорт и форма данных

- `scripts/import-compendium.py:import_option_blocks` собирает списки в `ClassOptionBlock { id, name, text, items }`; каждый `ClassOption` несёт `id`, `name`, `text`, `source: srd | book | hb`, иногда `srdName` и координату `cell`. Для блока подкласса проставляет `subclassId`.
- `mark_choice_placeholders` ищет совпадение имени строки уровня с именем варианта блока класса (только блока без `subclassId`) и превращает строку в placeholder: `ClassFeature.choice = block.id`, `name/text` подменяет данными блока. Связь — строковый id блока, не полноценная схема количества/допустимых источников/уровня выбора.
- Опции импортируются после строк уровней. У блока нет `level`, `count`, `repeatSchedule` или указания, какая именно feature разрешает выбор. Подклассовые опции не связываются с placeholder общим способом.
- `src/rules/compendium/schema.ts` типизирует эту ограниченную форму. `content/compendium/classes.json` содержит конкретные импортированные данные, но их наличие не включает выбор в интерфейс/расчёт автоматически.

### Как это связано с листом

- `PcSpec.choices` и `Draft.choices` — `Record<string, string[]>`. Редактор отображает `derived.featureChoices`, а `toSpec` копирует эти ID без дополнительной provenance.
- `deriveCharacter` берёт `featureChoices` из `classChoicesOf` и расовых фабрик; выбранные ID проверяются против `FeatureChoice.options`, а в `CharacterSheet.choices` (`ChosenFeature[]`) сохраняются `{ id, label, values: [{id,name}] }`.
- В `build.ts` `classChoicesOf` вызывает `srdIdOf(cls)` и сразу возвращает `[]` для класса вне SRD. Поэтому, например, импортированный класс Изобретатель не получит generic class options в редакторе, даже при наличии импортированного блока «Инфузии изобретателей». Встроенные правила охватывают фиксированный набор SRD: стиль (только таблица блока по имени), ranger enemy/terrain, метамагия (табличный блок по имени), драконьего предка и Expertise. Это не отражает все уровни роста выбора из imported options и не покрывает subclass option blocks.
- `CharacterEditor` показывает классовые `FeatureChoice` через `ChoiceBlock`; варианты вне SRD помечает бейджем «книга». Но список источников здесь берётся из уже построенного `FeatureChoice`, а не напрямую из полного каталога `cls.options`. Текущий класс/подкласс может сбрасывать зависимые `Draft.choices`, но сам generic импортированный список не появляется.
- `sheet.choices` содержит только выбранные значения и подписи: нет уровня приобретения, `source`, редакции/слоя, id блока/владельца или истории выбора. Текущая агрегация полезна для полного листа персонажа, но недостаточна для надёжного аудита повторных выборов и отображения конкретного level-up.

### Повышение и план

- `levelUpPlan` предлагает подкласс, ASI/черту и некоторые SRD-заклинания. В `LevelUpChoice` нет поля для class/subclass feature choices; `LevelUpForm` поэтому их не может собрать.
- `levelUp` получает `subclassId`, затем безусловно добавляет все features строки уровня и выбранного подкласса в `sheet.features`. Для вычисления атак читает только `sheet.choices.find(id === 'fighting-style')`.
- `previewLevelUp` выдаёт warning по `pathFeatureKind(feature) !== 'level'`: эвристика учитывает `feature.choice`, слэш в имени и отдельные русские слова. Но `levelUp` уже создал лист с feature; warning не блокирует подтверждение и не записывает решение.
- `calculateLevelPlan` останавливается на warnings и оставляет такой шаг кандидатом вне рассчитанного actor. Это защищает дальний расчёт от неполноты, но не добавляет UI/контракт выбора. Сам `LevelPlan` хранит решения только в React state до сворачивания/уничтожения формы (по контексту — локальный draft); generic choice там также отсутствует.

## План реализации полного БА27

Сохранять границу «источник говорит, что выбирать; движок применяет только доказанные эффекты». Не выводить число/условие из текста и не превращать один placeholder в автоматически полученное умение.

### 1. Зафиксировать контракты и миграцию данных

Файлы: `src/rules/compendium/schema.ts`, при необходимости отдельная `src/rules/compendium/classChoices.ts`; импортёр `scripts/import-compendium.py` менять лишь если исходная таблица позволяет достоверно извлечь недостающую структуру.

Добавить optional source-aware описание требования выбора с полями примерно:

```ts
interface ClassChoiceDefinition {
  id: string;                 // стабильный id опции/feature
  owner: { classId: string; subclassId?: string };
  featureId: string;          // точная связь с ClassFeature
  label: string;
  source: Source;
  ruleset?: { id: string; version: string; layer: string };
  acquisition: { levels: number[]; countAtLevel: number };
  options: ClassOption[];     // у каждой сохраняются source, cell, srdName
  resolution: 'informational' | 'supported';
  effectAdapter?: string;     // только зарегистрированный адаптер
}
```

`levels/countAtLevel` заполнять лишь из явно сопоставленных таблиц/правил; неизвестное оставлять `undefined`/`informational` и отображать первичный текст с `cell`. Не делать регэксп по прозе источником механики. Существующую `ClassOptionBlock` оставить совместимой; derived catalog строить из явных связей, отдельные ручные SRD-правила постепенно переоформлять тем же контрактом. Не генерировать файлы без согласования Codex.

### 2. Сделать единый каталог предложений и валидацию

Файлы: `src/campaign/build.ts`, `src/campaign/derive.ts`, `src/campaign/path.ts`, тесты `build.test.ts`, `derive.test.ts`, `progression.test.ts`.

- Добавить pure-функцию предложений по `(classId, subclassId, classLevel, sourcePolicy/ruleset)`; возвращать определения с явным источником, уровнем/числом выбора и причиной `informational`, если сведений недостаточно.
- Редактор начального персонажа продолжает использовать каталог и общий контрол; проверка `PcSpec.choices` валидирует только требования, которые каталог реально разрешил на выбранном уровне. Не предлагать options неподключённой ветви.
- Старые ручные SRD выборы (enemy/terrain/expertise/dragon ancestor) имеют regression-тесты: сохранить их текущие уровни, counts и ограничения. Источник выбора не должен расширяться из-за просто присутствующей в JSON книжной опции.

### 3. Поддержать решения шага повышения

Файлы: `src/campaign/levelUp.ts`, `levelUpPreview.ts`, `levelPlan.ts`, `src/components/LevelUpForm.tsx`, `LevelPlan.tsx`; связанные модели в `src/campaign/derive.ts`, `src/engine/characterLevel.ts` и типе `CharacterSheet` найти и обновить с обратной совместимостью.

- Расширить `LevelUpPlan` данными требований текущего уровня и выбранного подкласса; `LevelUpChoice` получает отдельное поле, например `featureChoices: Record<choiceId, string[]>`. Переиспользовать `ChoiceBlock`-подобный доступный контрол, с количеством/ограничениями и полным текстом/source.
- Валидировать обязательные и повторяемые picks только по явной схеме. Неизвестная схема должна запрещать точное применение этого шага или оставить его кандидатом с ясной диагностикой; простое подтверждение без выбора недопустимо.
- В событии `CHARACTER_LEVELED` уже хранится снимок листа, поэтому решения должны попасть в этот snapshot и сохраняться/replay/undo вместе с повышением. Расширить choice record optional `at`, `source`, `ruleset`, `owner/featureId` или хранить append-only записи приобретения отдельно; старые агрегированные `ChosenFeature` записи читаются как legacy без выдуманной даты/source. Дедупликация должна позволять выбор одной опции повторно только если правило допускает.
- Для `levelPlan` хранить выборы вместе с шагом, передавать их в превью, и считать следующий уровень от результата только если все choice requirements разрешены.

### 4. Связать применение с механикой только через явные адаптеры

Файлы по мере доказательства: `src/campaign/levelUp.ts`, `src/campaign/build.ts`/`derive.ts`; отдельный `src/campaign/classChoiceEffects.ts` предпочтительнее растущих условий в `levelUp`.

- Начать с тех выборов, эффекты которых уже поддержаны типизированными правилами и доказуемо соответствуют источнику/редакции (например существующий SRD fighting style `Archery` для атак). Сохранить `source + ruleset/version + effectAdapter` рядом с каждым применением.
- Все прочие решения показывать/сохранять как полученные из источника, но не выдавать непроверенное изменение AC, ресурсов, атак, действий или условий. Строки `text`, `srdName`, имя блока или наличие options недостаточны для эффекта.
- При неподдержанном эффекте показать “решение сохранено, механический расчёт не поддержан” и не маркировать предпросмотр как полный. Разделить предупреждения о текстовом описании и реально незавершённое обязательное решение.

### 5. Согласовать проекцию и финальный UI

Файлы: `src/campaign/path.ts`, `src/components/CharacterPathView.tsx` и тесты; затем интеграция в `LevelUpForm`/`LevelPlan`.

Узел должен различать автоматическое получение, явно сформулированный выбор, неполную схему и неподдержанный эффект; показывать source/ruleset/ячейку таблицы, когда доступна. Сравнение подкласса остаётся только просмотром. Подтверждённые решения брать из листа по уровню/feature, а не выводить из достигнутого уровня. Если в источнике нет ясного числа/момента — показывать текст с пометкой «структуру выбора нужно проверить», не угадывать.

## Риски и совместимость

- Риск ложной полноты из `ClassFeature.choice`: поле сейчас только указывает placeholder на option block; не говорит, сколько вариантов выбирать, когда выбирать и как они применяются.
- Источники смешаны в `ClassOptionBlock.items`; фильтр по source уже существует в редакторе/проекции, но применение выбора требует явного ruleset/layer. Не позволять значениям из книги влиять на SRD-only лист.
- `CharacterSheet.choices` агрегирует текущие значения и не хранит историю; миграция старых snapshots/events должна принимать прежнюю форму.
- Дублирующее хранение в `sheet.features` и в выбранных values может ошибочно пометить placeholder/альтернативу как отдельную автоматически полученную способность.
- Применение bonus/feature до наличия effect adapter может дать неправильные AC/урон/ресурсы; оставлять информационным и warning-ить точную область неполноты.
- Импортёр содержит эвристики табличной раскладки и ручные поправки. Нельзя запускать генератор на общей грязной копии до отдельной координации; ручные контрактные данные должны быть reviewable и привязаны к координатам исходника.

## Meaningful tests

1. Импорт/schema fixture: импортированный class option и subclass option сохраняют id/source/text/cell; только подтверждённая строка связывается с feature; неизвестная связь/счётчик остаётся informational. Fixture на таблицу без достаточных данных предотвращает эвристическое угадывание.
2. Общий каталог: таблицы по всем 13 классам и 112 subclass ветвям; source filtering; получение на правильном уровне; отсутствие опций соседней ветви; регрессия текущих SRD class choices/counts.
3. Editor/derive: выбор валидируется по разрешённым options и count; недопустимый source/дубликат/не тот уровень отклоняются; новый каталог выводится тем же путём, что интерфейс показывает.
4. Level-up: обязательный выбор нельзя пропустить; неподдержанная схема блокирует точный apply; поддержанное значение оказывается в итоговом листе/event snapshot; preview equals replay; undo возвращает исходный лист; reload/replay сохраняет provenance.
5. План: раннее изменение/удаление подкласса или выбора отбрасывает зависимые последующие решения; candidate остаётся вне итогового actor; informational выбор не протекает в полный итог; исходный actor не мутирует.
6. Path UI unit/accessibility: выбор и автоматическое умение различимы текстом, source/ячейка читаются, клавиатурная навигация работает, сравнение ветви не меняет выбранную ветвь/лист. Это не заменяет согласованную браузерную визуальную приёмку.
