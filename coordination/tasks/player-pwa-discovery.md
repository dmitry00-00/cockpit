# Discovery: минимальный PWA для игрока

Read-only аудит источников проекта на 03.11.2026. Код, маршруты, хранилище и манифесты не менялись. Термин «PlayersView» ниже означает существующий режим интерфейса; компонента страницы `PlayersView.tsx` в `src/` нет — есть только его тест `src/pages/PlayersView.test.tsx`.

## Инварианты, обязательные для игрокового клиента

- Источник состояния — журнал событий; принятые изменения мира должны реплеиться, отменяться и переживать перезагрузку. Навигация и UI-состояние событиями не являются. Сверено по `CLAUDE.md` («Механика», «Состояние», «Правила экрана»), `src/engine/persist.ts` и `src/engine/store.ts`.
- Проекция игрока должна исключать секреты уже из передаваемых/сохраняемых данных и DOM, включая метаданные и скрытые ссылки. Скрытое нельзя послать целиком, положиться на CSS или отфильтровать только после загрузки на устройство игрока.
- Монстров игрокам показывают словами о состоянии, без HP/AC/CR/блока. Заметки мастера секретны по умолчанию; игрокам показывают лишь специально открытые заметки.
- Симуляция и импорт сами не меняют мир. Игроковый транспорт не должен создавать/принимать мировые патчи; это отдельное решение мастера и типизированный путь событий.

## Минимальный полезный полный срез

Рекомендуемый первый релиз — **read-only PWA-экран игрока с одним закреплённым героем**, который получает актуальный разрешённый снимок кампании. Он должен уметь:

1. Открыть карточку/лист назначенного героя: характеристики и игровые значения, классовый путь, известные умения/заклинания, ресурсы, снаряжение, HP и состояния этого PC.
2. Показать контекст, без которого героем неудобно играть: публичный состав/статусы партии, чей ход и публичный порядок, известное место/сцена/карта, время/погода, общие заметки и записи журнала, открытые знания. Не показывать монстру числовые статы, блок или скрытые данные.
3. Работать после установки как PWA: оболочка и статические публичные ресурсы доступны офлайн; последний разрешённый игроковый снимок может быть только read-only, явно помечен временем получения и состоянием «нет связи». При потере связи нельзя изображать живое обновление.
4. Не включать в v1 изменение кампании, броски/ходы от имени игрока или принятие предложений. Потребность в действиях игрока позже решается отдельными типизированными командами с проверкой роли на доверенной стороне.

### Как игрок получает своего героя

Нужна новая привязка, которой сейчас нет. Минимальная модель: мастер в своём клиенте выбирает существующего PC и выпускает короткоживущий одноразовый код/QR для подключения. При его погашении доверенная сторона закрепляет серверную identity игрока за конкретным `actorId` и выдаёт ограниченный session credential. Клиент получает только DTO для этого PC и общего разрешённого контекста. Отозванное/повторно использованное приглашение не должно выдавать данные; перевод героя требует явного действия мастера. Не использовать общий пароль кампании, клиентский фильтр полного журнала или перебор списка актёров на телефоне.

Вариант «игрок сам выбирает любого `actorId` из локального сид-ростера» не выполняет привязку и открывает чужие листы. Демонстрационный сид не должен выдаваться за синхронизированную живую кампанию.

## Что требует нового транспорта и storage boundary

Минимальный transport — доступный с телефона HTTPS endpoint доверенного хоста кампании с кодом присоединения и серверной таблицей `player session → actorId`. Для одного локального стола его можно обслужить отдельным процессом/сервером, но доступность телефона в той же сети и HTTPS должны быть явно устроены. Существующие MapTool endpoints нельзя использовать как подмену: они не имеют авторизации/идентичности игрока, держат только MapTool relay в памяти dev-server и не передают campaign projection.

После проверки invitation сервер/хост строит **allowlist projection перед отправкой**: только данные назначенного PC, публичный shared state, открытые знания/места и разрешённый журнал. Нельзя отправлять полный `State`, `DomainEvent[]`, исходный `EntityView`, мастерские `Fact`, все нити, сырые метаданные, причины скрытых событий или карты/ссылки с закрытыми объектами. Нельзя писать `dm-cockpit:log` на устройство игрока. Это обеспечивается отдельным API/store; текущий `localStorageStore` нельзя переиспользовать для PWA.

PWA-хранение ограничить versioned player DTO, отделённым по campaign и actor session. Service worker кэширует только shell и статические ресурсы; player API отвечает `Cache-Control: no-store` и исключён из Cache API. Для offline last snapshot — если он нужен — сохраняется отдельным player-only механизмом после серверной проекции и помечается stale; при logout/revoke приложение очищает токен и этот snapshot. Известная копия у устройства игрока не содержит мастерских payloads по конструкции, а не за счёт последующей очистки.

Для живых обновлений transport должен передавать revision/sequence и heartbeat, выдавать актуальный snapshot после reconnect и позволять клиенту обнаружить пропуск/устаревшие данные. UI показывает только фактически подтверждённое соединение, время последней синхронизации и ошибку/офлайн; MapTool `seenMsAgo` не является сигналом соединения игрока.

## Рекомендуемое разделение модулей

- **`src/player/` (новый клиентский срез):** player DTO types, отдельный store для разрешённого projection, join/reconnect/offline state и player route/view. Он не импортирует DM store/persist или `seedEngine`.
- **Доверенная сторона кампании (новый сервер/host module):** invitation issuance/revocation, binding actor, allowlist projector, authenticated snapshot/subscription endpoint, revision/heartbeat. Проекция — чистая функция с положительным allowlist, а не удаление известных secret-ключей из сериализованного master state.
- **Service worker/static PWA:** отдельный app shell и публичные assets; denylist/no-store для всех player endpoints. Shell можно обновлять независимо от текущей версии DTO; несовместимую схему надо остановить с понятной ошибкой, а не читать master log.
- **Игровой движок:** остаётся источником истины на доверенной стороне. Для первого выпуска player DTO read-only; если позднее появится игроковое действие, принимать конкретную typed command с actor ownership validation и записывать событие на host.

## Meaningful tests для реализации

1. **Projection unit / adversarial fixtures:** в state одновременно hidden roll label/formula/metadata, DM facts, private notes, accepted/rejected/reroll delta with causes, DM thread links, NPC social values, secret map pins, monster CR/AC/HP/action block, public counterparts. Проверять сериализованный payload глубокой проверкой строк и ключей — ничего из запретного не входит; безопасные открытые факты входят.
2. **Actor scope:** выдача invite для Bo даёт его лист и только разрешённую общую партию; не содержит листов Korrin/Lyra/Aldric, смена `actorId`, истёкший/погашенный/revoked code отклоняются. Права проверяются на каждой подписке/reconnect, а не только в join.
3. **Transport integration:** два клиента, одно обновление мастера, sequence/heartbeat, reconnect после разрыва, пропущенная revision → новый snapshot, отозванный клиент прекращает получать данные. Проверить no-store headers и отсутствие CORS/room cross-talk при двух кампаниях.
4. **Cache/storage boundary:** инспекция всех Cache API/IndexedDB/localStorage entries после join и обновления с sentinel-секретами: только app shell плюс безопасный actor DTO; API не в SW cache, `dm-cockpit:log` отсутствует; logout/revoke стирает player token и локальную проекцию.
5. **DOM privacy regression:** расширить adversarial `PlayersView.test.tsx` для настоящего route/client и проверять весь `document.body` (`textContent`, `innerHTML`, `title`, `aria-*`, `data-*`, `href/src`, порталы), включая загрузку, обновление, offline и переходы. Текущий тест доказывает только UI-фильтрацию того же полного store.
6. **PWA behavior:** manifest/install metadata, service worker update, offline shell boot, stale-state notice with timestamp, retry/reconnect, unsupported browser fallback. Проверить mobile browser реальные состояния/viewport отдельно от jsdom.

Итог: сейчас готова сильная **UI-проекция** и офлайн-сохранение **master event log**, но нет player identity, player route, безопасной серверной проекции, общего транспорта или PWA оболочки. Первая полезная версия возможна после этих четырёх новых границ; переключение `P` текущего стола её не заменяет.
